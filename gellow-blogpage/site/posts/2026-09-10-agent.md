# 1. 什么是 Agent？

## 1.1 最简单的理解

传统的大语言模型更像一个“回答问题的模型”：

```text
用户输入
   ↓
LLM
   ↓
文本输出
```

例如：

```text
用户：北京现在天气怎么样？
LLM：我无法获得实时天气……
```

模型本身并没有真正访问天气服务。

而 Agent 的核心思想是：

> 让大语言模型不仅“回答问题”，还可以根据目标主动决定下一步要做什么，并调用外部能力完成任务。

一个非常典型的 Agent 流程：

```text
用户提出任务
    ↓
LLM 分析任务
    ↓
判断是否需要工具
    ↓
调用工具
    ↓
得到工具结果
    ↓
LLM 继续推理
    ↓
必要时再次调用工具
    ↓
输出最终答案
```

例如：

```text
用户：
帮我查一下哈尔滨明天天气，如果下雨就提醒我带伞。

Agent：
1. 判断需要天气信息
2. 调用天气 API
3. 获取天气结果
4. 判断是否有雨
5. 生成提醒
```

因此可以粗略写成：

```text
Agent = LLM + Tool + State + Control Loop
```

更完整一些：

```text
Agent =
LLM
+ Prompt / Instructions
+ Tools
+ Memory
+ State
+ Planning
+ Execution Loop
+ Guardrails
+ Observability
```

# 2. Agent 和普通 LLM 最大的区别

普通 LLM 通常是一次性的：

```text
Input → Model → Output
```

Agent 则通常包含一个循环：

```text
          ┌─────────────┐
          │   用户任务   │
          └──────┬──────┘
                 ↓
          ┌─────────────┐
          │ LLM 分析状态 │
          └──────┬──────┘
                 ↓
         是否需要执行动作？
          ↙            ↘
        是               否
        ↓                 ↓
   调用工具            输出结果
        ↓
   获得 Observation
        ↓
    更新当前状态
        ↓
      再次推理
        └───────────────→
```

也就是说：

> Agent 最核心的地方不是“用了大模型”，而是大模型处在一个可以不断观察、决策、执行、再观察的控制循环中。

---

# 3. Agent 的核心循环

很多 Agent 都可以抽象成：

```text
Observe → Think → Act → Observe → Think → Act ...
```

也可以写成：

```text
Observation
    ↓
Reasoning
    ↓
Action
    ↓
Environment
    ↓
New Observation
```

如果借用强化学习里的表达：

```text
状态 S
 ↓
策略 π
 ↓
动作 A
 ↓
环境变化
 ↓
新状态 S'
```

只不过现在的“策略”通常由 LLM 实现。

---

# 4. Agent 的几个核心组成部分

---

## 4.1 LLM：Agent 的决策核心

LLM 通常负责：

- 理解用户目标
- 分析当前任务
- 判断是否需要工具
- 选择调用哪个工具
- 填写工具参数
- 判断工具结果是否足够
- 决定是否继续执行
- 生成最终答案

因此：

```text
LLM ≈ Agent 的大脑
```

但这种说法只是方便理解。

实际上一个 Agent 系统里还可能存在：

```text
LLM
规则系统
状态机
工作流
数据库
工具系统
权限系统
```

真正生产级的 Agent 通常不是“所有事情都交给 LLM 自由发挥”。

---

## 4.2 Prompt / Instructions

Agent 一般需要一套系统指令。

例如：

```text
你是一个服务器运维助手。

你可以：
- 查询服务器状态
- 查询日志
- 重启服务

在执行重启等危险操作之前必须获得用户确认。
```

Prompt 通常定义：

```text
角色
目标
允许做什么
禁止做什么
工具使用原则
输出格式
异常处理原则
```

因此 Agent 的 Prompt 更像：

```text
运行策略 + 行为规范
```

而不仅仅是“你是一个有帮助的助手”。

---

## 4.3 Tools

工具是 Agent 与外部世界交互的核心。

例如：

```text
天气 API
搜索引擎
数据库
Python
Shell
GitHub
浏览器
文件系统
邮件
日历
Minecraft Server API
机器人 API
```

一个工具可能定义成：

```python
def get_weather(city: str) -> dict:
    ...
```

模型看到的可能是：

```json
{
  "name": "get_weather",
  "description": "获取城市天气",
  "parameters": {
    "city": "string"
  }
}
```

然后 LLM 决定：

```text
调用：
get_weather(city="Harbin")
```

这就是 Tool Calling / Function Calling 的基本思想。

---

# 5. Function Calling / Tool Calling

Function Calling 是 Agent 最重要的技术基础之一。

它解决的问题是：

> 如何让大模型从“生成自然语言”变成“生成结构化的程序调用”。

例如用户输入：

```text
查一下哈尔滨天气
```

模型不直接输出：

```text
哈尔滨今天……
```

而是可能输出：

```json
{
  "tool": "get_weather",
  "arguments": {
    "city": "哈尔滨"
  }
}
```

程序收到以后：

```python
result = get_weather("哈尔滨")
```

得到：

```json
{
  "temperature": -5,
  "weather": "snow"
}
```

再把结果返回给 LLM：

```text
Tool Result:
temperature = -5
weather = snow
```

模型最后生成：

```text
哈尔滨当前约 -5°C，并且有雪。
```

完整过程：

```text
User
 ↓
LLM
 ↓
Tool Call
 ↓
Application
 ↓
API / Function
 ↓
Tool Result
 ↓
LLM
 ↓
Final Answer
```

---

# 6. Tool 和 Agent 的关系

一个很容易混淆的问题：

> “只要调用工具就是 Agent 吗？”

不一定。

例如：

```python
if user_input == "天气":
    get_weather()
```

这是普通程序逻辑。

即使你用了 LLM：

```text
用户
 ↓
LLM 判断工具
 ↓
调用一次工具
 ↓
回答
```

也只能说它具有 Agentic 特征。

更加典型的 Agent 会包含：

```text
自主决策
多步执行
状态维护
错误恢复
工具选择
任务终止判断
```

因此 Agent 更像一个连续执行系统，而不是单次 Function Calling。

# 7. Workflow 和 Agent 的区别

Workflow：

```text
步骤 A
 ↓
步骤 B
 ↓
步骤 C
```

执行顺序提前写好。

例如：

```text
上传 PDF
 ↓
解析 PDF
 ↓
切片
 ↓
Embedding
 ↓
写入向量数据库
```

这是 Workflow。

Agent：

```text
当前任务是什么？
 ↓
我应该做什么？
 ↓
选择下一步动作
 ↓
执行
 ↓
重新判断
```

它的下一步不完全固定。

---

## 7.1 Workflow 的优点

Workflow：

```text
可预测
容易 Debug
便宜
稳定
执行流程固定
```

---

## 7.2 Agent 的优点

Agent：

```text
灵活
能够处理开放任务
能够动态选择工具
能够处理未知流程
```

---

## 7.3 生产环境通常是混合架构

非常常见：

```text
Workflow
   ↓
某一步进入 Agent
   ↓
Agent 完成动态任务
   ↓
回到 Workflow
```

因此不要认为：

```text
Agent > Workflow
```

实际上：

```text
确定性任务 → Workflow
不确定任务 → Agent
```

---

# 8. Agentic Workflow

近年来经常出现：

```text
Agentic Workflow
```

它处于：

```text
传统 Workflow
      ↓
Agentic Workflow
      ↓
完全自主 Agent
```

之间。

例如：

```text
生成文章
 ↓
自动检查
 ↓
如果不合格 → 修改
 ↓
重新检查
 ↓
合格 → 输出
```

这里不是完全开放的 Agent，但已经存在：

```text
反馈
循环
动态决策
```

所以具有 Agentic 特征。

# 9. ReAct

Agent 中非常经典的一种思想是：

```text
ReAct
```

来自：

```text
Reasoning + Acting
```

核心结构：

```text
Thought
Action
Observation
Thought
Action
Observation
...
Answer
```

例如：

```text
Question:
哈尔滨明天天气怎么样？

Thought:
我需要获取天气数据。

Action:
weather("哈尔滨")

Observation:
明天小雪，-10°C ~ -4°C。

Thought:
已经得到足够信息。

Answer:
哈尔滨明天有小雪……
```

ReAct 的关键思想是：

> 推理与行动交替进行。

不是：

```text
先想完所有步骤
再执行
```

而是：

```text
想一点
做一步
观察结果
再想下一步
```

# 10. Planning：任务规划

复杂 Agent 往往需要 Planning。

例如任务：

```text
分析这个 GitHub 项目并给出重构方案。
```

Agent 可能先规划：

```text
1. 查看目录结构
2. 查看 README
3. 找入口文件
4. 分析依赖
5. 分析核心模块
6. 找架构问题
7. 输出重构方案
```

然后再执行。

因此可以设计：

```text
Planner
 ↓
Executor
 ↓
Reviewer
```

---

# 11. Plan-and-Execute

一种常见架构：

```text
用户任务
  ↓
Planner
  ↓
任务列表
  ↓
Executor
  ↓
执行任务
  ↓
检查是否完成
  ↓
必要时重新规划
```

例如：

```text
Plan:
[1] 搜索资料
[2] 整理数据
[3] 生成报告
```

Executor 逐步执行。

优势：

```text
更适合长任务
更容易观察任务进度
规划和执行可以使用不同模型
```

例如：

```text
Planner → 强模型
Executor → 小模型
```

降低成本。

```text

```

流程：

```text

 ↓

 ↓
发现问题
 ↓
重新生成
```

例如代码 Agent：


实际上：

```text

```

# 13. Self-Correction

一个常见 Agent Loop：

```text
执行
 ↓
失败
 ↓
读取 Error
 ↓
分析原因
 ↓
修改方案
 ↓
再次执行
```

例如：

```text
python script.py
```

报错：

```text
ModuleNotFoundError
```

Agent：

```text
分析：
缺少 requests

动作：
pip install requests
```

然后重新执行。

这就是：

```text
Observe → Correct → Retry
```

# 14. Memory

Agent Memory 是非常重要的一部分。

Memory 并不是一个单独技术。

它可能由很多层组成。

---

# 15. Short-Term Memory

短期记忆通常指：

```text
当前对话 Context
```

例如：

```text
User: 我的名字叫 Gellow
Assistant: 好

User: 我叫什么？
```

模型能够回答：

```text
Gellow
```

因为前面的消息还在 Context Window 里。

可以理解：

```text
Short-Term Memory ≈ Context
```

---

# 16. Session Memory

如果用户关闭页面之后再次回来：

```text
之前聊天记录
```

可能存储在：

```text
SQLite
PostgreSQL
Redis
MongoDB
云数据库
```

下一次聊天时重新加载。

例如：

```text
session_id = user_123
```

数据库：

```text
session_123:
- message1
- message2
- message3
```

每次请求：

```text
load history
 ↓
LLM
 ↓
save new messages
```

---

# 17. Long-Term Memory

长期记忆通常不会保存所有对话。

而是保存：

```text
用户偏好
长期事实
历史决策
项目背景
```

例如：

```json
{
  "user_name": "Gellow",
  "preferred_language": "Chinese",
  "project": "knowledge-assistant"
}
```

或者使用向量数据库：

```text
过去的 Memory
 ↓
Embedding
 ↓
Vector DB
 ↓
语义搜索
 ↓
找到相关记忆
```

然后动态插入 Context。

# 19. Agent + RAG

这是非常常见的一种组合。

RAG：

```text
问题
 ↓
Retriever
 ↓
知识库
 ↓
Relevant Documents
 ↓
LLM
 ↓
Answer
```

Agent + RAG：

```text
问题
 ↓
Agent
 ↓
判断是否需要知识
 ↓
调用 Retriever Tool
 ↓
搜索知识库
 ↓
返回 Documents
 ↓
Agent
 ↓
继续推理
```

最大的区别：

传统 RAG：

```text
每次都检索
```

Agentic RAG：

```text
Agent 自己判断是否需要检索
```

# 20. Agentic RAG

Agentic RAG 可以进一步加入：

```text
Query Rewrite
Search
Rerank
Evaluate
Retry
```

例如：

```text

 ↓
Agent 判断问题
 ↓
Rewrite Query
 ↓
Vector Search
 ↓

   ↓否
重新搜索
   ↓
找到足够资料

```

这就是：

```text
Retrieval Loop
```

# 21. 为什么 Agent 和 RAG 是两种不同东西？

RAG解决：

```text
模型不知道某些知识怎么办？
```

Agent解决：

```text
模型如何完成一个任务？
```

因此：

```text
RAG = Knowledge Access
Agent = Task Execution
```

Agent 可以调用 RAG：

```text
Agent
 ├─ Search Tool
 ├─ RAG Tool
 ├─ Database Tool
 └─ Python Tool
```

所以：

> RAG 可以成为 Agent 的一个工具。

# 28. State

Agent 必须知道：

```text
当前做到哪一步了
已经获得什么信息
下一步应该做什么
```

因此需要 State。

例如：

```python
state = {
    "question": "...",
    "documents": [],
    "plan": [],
    "current_step": 2,
    "tool_results": [],
    "final_answer": None
}
```

整个 Agent 实际上一直在：

```text
State → Node → New State
```

# 31. LangGraph 最重要的三个概念

---

## 31.1 State

保存整个执行状态。

例如：


# 35. Checkpoint

# 40. MCP

MCP：


它解决的问题可以简单理解为：

> 如何用一种统一协议，把外部工具和数据源提供给 AI 应用。

传统情况：

```text
Agent
 ├─ GitHub API Adapter
 ├─ Database Adapter
 ├─ Slack Adapter
 ├─ Files Adapter
 └─ Browser Adapter
```

每个都单独开发。

MCP 希望变成：

```text
Agent
 ↓
MCP Client
 ↓
MCP Protocol
 ↓
MCP Server
 ↓
External Service
```


```text

- create_issue

```

Agent 只需要通过 MCP Client 连接。

# 42. MCP 和 Tool Calling 的区别

Tool Calling：

```text

```

MCP：

```text

```

所以可以理解：

```text

MCP = 工具连接协议
```

它们不是竞争关系。

而是：

```text
MCP Server
 ↓
提供 Tools
 ↓
LLM Tool Calling
 ↓
执行 Tool
```

# 43. MCP 和 API 的区别

```text

```

```text

```

MCP Server 内部仍然可以调用：

```text

GraphQL
Database
Local Program
```

因此：

```text
MCP ≠ 替代 API
```

而更像：

```text

```

# 95. 一个简单 Agent 的伪代码

```python
messages = [system_prompt, user_message]

for step in range(MAX_STEPS):

    response = llm(messages, tools=tools)

    if response.tool_calls:

        for call in response.tool_calls:

            result = execute_tool(
                call.name,
                call.arguments
            )

            messages.append({
                "role": "tool",
                "content": result
            })

    else:
        return response.text

raise RuntimeError("Agent exceeded max steps")
```

这个循环已经包含 Agent 最核心的结构：

```text
LLM
 ↓
Tool
 ↓
Observation
 ↓
LLM
```

# 98. Agent 和传统自动化的区别

传统自动化：

```text

```

Agent：


因此特别适合：



# 99. 哪些任务适合 Agent？

适合：



# 100. 哪些任务不适合 Agent？

不适合：

```text

稳定 ETL
明确 Workflow
高频低延迟请求
```

比如：

```text

```

完全没必要让 LLM 决定。

普通代码：

```text

```

更稳定。

```text
上传文件
```

都让 LLM 决定。

这是没有必要的。

# 155. Agent 工程原则

可以总结几个：

```text
能用代码解决 → 不用 LLM

能用 Workflow → 不用 Agent

能用单 Agent → 不用 Multi-Agent

能用小模型 → 不用大模型

危险操作 → 必须限制权限
```


# 160. 最后总结

最简单的 Agent 可以写成：

```text
Agent = LLM + Tools + Loop
```

工程化以后：

```text
Agent =
LLM
+ Tools
+ State
+ Memory
+ Planning
+ Workflow
+ RAG
+ MCP
+ Guardrails
+ Evaluation
+ Observability
```

如果是复杂系统：

```text
Agent System =
Multiple Agents
+ Shared State
+ Orchestration
+ Tools
+ Memory
+ Infrastructure
```

真正理解 Agent 的关键不是记住某个框架 API，而是理解：

```text
模型为什么调用工具？
工具结果如何返回？
状态如何保存？
下一步由谁决定？
什么时候结束？
失败以后怎么办？
如何限制权限？
如何判断任务真的完成？
```

一旦这些问题能够解释清楚：

```text
LangChain
LangGraph
OpenAI Agents SDK
CrewAI
AutoGen
```

其实都只是：

```text
不同形式的 Agent Runtime / Orchestration 实现。
```
