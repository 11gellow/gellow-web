# Gellow Web — 项目开发总规划

## 0. 项目定位与 Codex 职责

项目仓库：https://github.com/11gellow/gellow-web

本项目是一个长期维护的个人网站，同时也是开发者学习 Python Web 后端开发与软件工程的实践项目。

**项目的首要目标是通过实际开发提升开发者的编程与工程能力，其次才是功能开发速度。**

Codex 承担以下角色：

- 软件架构师：分析现有系统、设计模块边界与数据流。
- 工程开发助手：实现正式功能及开发者不熟悉的外围代码。
- 前端开发助手：协助完成 Vue、HTML、CSS 和页面交互。
- 测试工程师：提供单元测试、集成测试及验收方法。
- 代码审查员：检查代码质量、逻辑正确性和安全风险。
- 编程导师：配合独立的学习规范，帮助开发者逐步掌握 Python 后端代码。

项目采用**双分支教学驱动开发工作流**，具体规则见第二份《Gellow Web — 个人学习与双分支开发规范》。

两份规范必须同时遵守。

## 1. 项目现状

当前仓库主要包含三个部分：

- `gellow-homepage/`：个人主页，存在 Python Flask 后端。
- `gellow-blogpage/`：基于 VitePress、Vue 3 和 Markdown 的博客。
- `gellow-notespage/`：旧版 Notes 页面。

现有 Flask 后端使用过 Turso/libSQL，包含内容管理、附件、积分等接口。

当前 Blog 已主要转向静态 Markdown 架构，但仓库仍保留部分旧系统代码。

### 现有项目处理原则

- 不直接推倒重写整个网站。
- 尽可能保留现有 Blog 的像素风设计。
- 保留文章展示、播放器、小游戏等已有功能。
- 优先复用合理的代码和基础设施。
- 对历史遗留代码先确认用途，再决定保留、迁移或删除。
- 不根据过时 README 直接推断项目现状。
- 不为追求新技术而盲目更换框架。

正式开发前必须对当前仓库进行实际审查。

## 2. 总体需求

### 2.1 公开 Blog

所有访客均可以：

- 访问公开博客。
- 阅读公开文章。
- 浏览公开内容与链接。
- 使用现有公开互动功能。

公开 Blog 继续使用 VitePress + Markdown 架构。

### 2.2 用户注册与登录

支持：

- 用户名、邮箱、密码注册。
- 本地账号登录与退出。
- 查询当前登录用户。
- 基本用户资料管理。
- GitHub 第三方登录。
- Google 第三方登录。
- 本地账号与第三方身份绑定。
- 账号禁用与恢复。

Google 登录使用标准 OpenID Connect，GitHub 登录使用标准 OAuth 流程。

认证协议及密码学功能使用成熟库，不自行实现安全底层。

### 2.3 权限管理

采用 RBAC（基于角色的访问控制）。

初始角色：

| 角色 | 说明 |
|---|---|
| guest | 未登录游客 |
| user | 普通注册用户 |
| note_reader | 可阅读受保护笔记 |
| admin | 系统管理员 |

初始权限可包括：

- `note:read`
- `user:read`
- `user:manage`
- `role:assign`

角色与权限的具体关系由后端维护。

权限判断必须在服务端完成，不能依赖前端隐藏按钮。

### 2.4 管理员后台

管理员可以：

- 查询用户列表。
- 查看用户详情。
- 搜索用户。
- 修改用户角色。
- 启用或禁用账号。
- 查看用户权限。
- 管理必要的系统配置。

第一版管理员后台优先采用 Flask + Jinja2。

界面不要求复杂，能够完成实际操作即可。

### 2.5 私有 Note

只有具有 `note:read` 权限的用户可以访问受保护笔记。

需解决现有 VitePress 静态生成的问题：

- 私有笔记不得包含在公共静态构建产物中。
- 私有笔记不得继续以明文放在公开 Git 仓库里。
- 私有内容通过经过后端鉴权的接口或服务端页面提供。
- 未授权用户不得通过直接访问 URL 或静态资源绕过权限。
- 附件、图片等私有资源也应遵循访问控制。

开发初期可先使用模拟内容验证授权流程，暂不迁移真实笔记。

## 3. 技术栈与架构原则

优先采用：

| 领域 | 技术 |
|---|---|
| 后端 | Python + Flask |
| 公开博客 | VitePress + Vue 3 |
| 管理后台 | Flask + Jinja2 |
| 数据库 | 优先评估现有 Turso/libSQL |
| 本地开发 | SQLite 或兼容数据库 |
| 密码哈希 | Werkzeug 等成熟库 |
| 第三方认证 | Authlib 等标准协议库 |
| 授权模型 | RBAC |
| 自动化测试 | pytest |
| 依赖管理 | 优先评估 uv + pyproject.toml |
| 部署 | 优先兼容现有 Vercel 架构 |

具体技术选择必须先核查兼容性，再写入技术决策文档。

### 架构原则

1. 模块化单体，不使用微服务。
2. 路由层、业务逻辑层、数据访问层尽可能职责清晰。
3. API 设计保持简单、稳定。
4. 不引入没有实际需求的抽象层。
5. 不为未来不确定的需求过度设计。
6. 可以先做简单实现，再根据实际问题重构。
7. 保持模块可测试，避免所有代码继续堆积在单个 `app.py` 中。

暂不引入 Redis、Celery、消息队列、Kubernetes 等非必要基础设施。

## 4. 目标系统架构

总体上分为两个主要部分。

### 公开网站

由 VitePress 提供：

- Blog 首页。
- 公开文章。
- 现有交互页面。
- 登录与用户状态展示入口。

### Flask 后端

提供：

- 注册与登录。
- Session 管理。
- 第三方登录。
- 用户管理。
- 角色与权限。
- 私有笔记接口。
- 管理员后台。

尽量采用同源 `/api/` 访问方式，通过合理的代理或路由配置减少 Cookie 与 CORS 问题。

### 建议后端目录

以下是目标结构，不要求一开始全部创建：

- `backend/app/__init__.py`：应用初始化。
- `backend/app/config.py`：配置。
- `backend/app/models/`：数据库模型。
- `backend/app/routes/`：HTTP 路由。
- `backend/app/services/`：业务逻辑。
- `backend/app/utils/`：工具函数。
- `backend/templates/`：Jinja2 模板。
- `backend/migrations/`：数据库迁移。
- `backend/tests/`：测试。
- `backend/pyproject.toml`：项目与依赖配置。

现有 Flask 文件的迁移方式由 Phase 0 决定，不允许直接覆盖旧代码。

- username

- updated_at

- id
- name
- description

- id
- code
- description

- user_id
- role_id

### role_permissions

- role_id
- permission_id

- id
- slug
- title
- content
- author_id
- status

数据库设计需要明确主键、唯一约束、外键与索引。

## 7. 安全要求

本项目允许逐步提高工程质量，但不允许将故意脆弱的认证系统公开部署。

基础安全要求包括：

- 密码使用成熟哈希算法。
- 服务端执行授权检查。
- Session Cookie 正确配置。
- 使用 CSRF 防护。
- 登录与注册接口设置基本限流。
- 数据库操作使用参数化查询。
- 不在代码中硬编码密钥。
- 不公开未授权的管理接口。
- 私有内容不能包含在公开构建产物中。

复杂风控、企业级审计、分布式认证等高级功能暂不实现。

当前仓库已经存在的高优先级风险，应在 Phase 0 明确处置方案；涉及公开可写接口的风险，在继续公网运行前需要优先隔离或修复。

## 9. 开发约束

- 每次只推进一个明确的任务或小模块。
- 不因为功能简单就忽略测试。
- 不因为使用 AI 就跳过代码审查。
- 不自动扩大任务范围。
- 不未经检查删除旧业务代码。
- 不覆盖开发者未提交的修改。
- 不擅自修改线上数据库。
- 不自动 Push、部署或合并 main。
- 正式功能提交遵守第二份学习规范的验收流程。

每次任务完成后更新相关项目文档。

## 10. Codex 收到规划后应当执行的第一步

从 Phase 0 开始。

先阅读仓库、分析实际架构、识别现存问题，建立项目文档并拆分任务。

同时阅读第二份学习规范，为后续双分支开发准备工作区方案。

第一轮只完成审查、文档和必要的安全风险报告，不直接实现整个用户系统，不修改现有业务代码。

完成后向开发者汇报：

1. 当前真实架构。
2. 推荐目标架构及理由。
3. 当前必须解决的问题。
4. 分阶段任务是否需要调整。
5. Phase 1 的第一个小任务。
6. 该任务适合采用什么教学难度。

**长期目标：在保留个人博客的基础上，逐步完成一套开发者真正理解、能够独立维护的 Python Flask 后端系统。**
