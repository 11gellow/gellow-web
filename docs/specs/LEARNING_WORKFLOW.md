# Gellow Web — 个人学习与双分支开发规范

## 0. 核心目标

本项目采用 **双分支教学驱动开发模式**。

开发者目前：

- Python 相对熟悉，但实际代码编写能力仍需提升。
- 能够理解一部分代码，却不一定能从空文件独立写出完整实现。
- 对大型项目的数据流、调用链、模块边界还不够熟悉。
- 希望通过真实项目逐渐形成独立编写、调试和维护代码的能力。

因此，不能要求开发者一开始就从零实现完整模块。

Codex 应先提供正确的项目结构与部分实现，再根据开发者能力留下需要亲手完成的代码。

随着能力提升，逐步减少辅助。

**最终目标是从“会理解和补全代码”，过渡到“会独立设计、编写、调试代码”。**

本规范以学习质量和真实工程能力提升为优先，而非开发速度。

---

# 1. 双分支工作流

项目保留三个主要分支。

## main：稳定版本

- 保存通过验收的正式网站代码。
- 不直接在 main 上进行练习。
- 不直接进行未经测试的功能开发。
- 只有完成集成验收的功能才可以合并。

## dev：正式开发分支

由 Codex 主要维护。

用于：

- 完成完整的功能实现。
- 编写正式测试。
- 验证架构与接口。
- 提供教学任务的参考实现。
- 整合开发者亲手完成的优秀代码。

dev 不保留故意错误和教学 TODO。

**当前正式开发任务在教学验收完成前，不执行最终功能 Commit。**

## learn：教学分支

由开发者主要编写。

Codex 负责准备练习环境。

允许存在：

- 未实现的函数。
- 缺失的代码片段。
- 需要调试的普通逻辑错误。
- 待重构代码。
- 教学注释与提示。

开发者主要在 learn 中写代码。

learn 不作为生产部署来源。

# 2. 工作区管理

优先采用 Git Worktree。

推荐目录：

- `gellow-web/`：main。
- `gellow-web-dev/`：dev。
- `gellow-web-learn/`：learn。

具体路径由 Codex 根据实际工作环境确定。

创建前必须检查：

- 当前 Git 状态。
- 是否存在未提交修改。
- 是否已经存在对应分支。
- 是否已经存在 Worktree。
- 是否有需要保留的用户文件。

不得强制覆盖或删除现有代码。

### 未提交代码的保护

由于 dev 的正式实现可能需要在学习期间保持未提交状态，Codex 必须做好本地恢复措施。

可以保存受控补丁、未跟踪文件清单和必要的本地快照，但不能将未提交修改视为已受 Git 版本保护。

不得使用可能丢失代码的强制 reset、clean、checkout 等操作。

正式版本与教学版本之间的文件同步需要显式管理。

**不能假设 dev 未提交的代码会自动出现在 learn 分支。**

如果开发者在 learn 中存在未完成修改，Codex 不得直接覆盖。

# 3. 标准开发与教学流程

每个实际业务任务按照以下流程进行。

## Step 1：任务设计

Codex 阅读：

- PROJECT.md
- ARCHITECTURE.md
- DECISIONS.md
- TASKS.md
- STATUS.md
- LEARNING.md

明确：

- 本次任务要实现什么。
- 涉及哪些模块。
- 需要哪些新知识。
- 哪些代码由 Codex 完成。
- 哪些代码适合作为练习。
- 本次练习难度。
- 本次验收条件。

任务应尽可能小。

初期每次只保留 1～3 个相互关联的练习点。

## Step 2：正式实现

Codex 在 dev 工作区完成当前功能的参考实现。

要求：

- 功能完整。
- 结构合理。
- 有必要的测试。
- 没有故意缺失的生产逻辑。
- 能解释主要调用链。

这份实现作为参考方案，暂不进行最终功能 Commit。

Codex 应保存可靠的恢复副本，避免长期未提交代码意外丢失。

## Step 3：生成教学版本

Codex 根据 dev 的实际开发任务，在 learn 中构造教学版本。

例如：

- 函数 A：保留函数签名，缺少实现。
- 函数 B：缺少部分逻辑。
- 函数 C：存在需要排查的普通 Bug。
- 函数 D：功能完整，但有重复代码需要重构。

教学代码必须来自真实业务需求，不额外制造大量无关习题。

Codex 应保留：

- 必要的项目结构。
- 函数签名。
- 上下文。
- 调用方。
- 必要的测试。
- 合理的实现提示。

不要把所有代码都挖空。

### 参考答案隔离

dev 中的完整参考实现，不应在开发者尝试练习之前主动展示。

开发者可以随时主动要求查看。

## Step 4：开发者亲手实现

开发者在 learn 中完成练习。

Codex 不主动直接填完 TODO。

允许：

- 查阅 Python 官方文档。
- 查阅 Flask 文档。
- 搜索对应技术资料。
- 使用 IDE 和调试器。
- 运行测试。
- 向 Codex 请求提示。
- 参考此前已经学过的代码。

Codex 应鼓励开发者先说出自己的实现思路，再尝试编码。

## Step 5：Code Review

开发者完成练习后，由 Codex 审查。

重点检查：

- 逻辑是否正确。
- 测试是否通过。
- 是否理解调用关系。
- 是否处理边界情况。
- 是否存在明显重复代码。
- 是否存在不合理的模块依赖。
- 是否有安全问题。
- 是否符合当前项目架构。

不要因为写法和 Codex 参考答案不同就判定错误。

优先判断行为是否正确，以及是否满足项目需求。

## Step 6：学习复盘

Codex 应总结：

- 本次涉及的 Python 知识。
- 实际运行过程。
- 开发者出现的典型错误。
- 造成错误的原因。
- 已经掌握的能力。
- 需要加强的能力。
- 下次可以增加的难度。

关键学习进展写入 LEARNING.md。

## Step 7：正式代码整合

这是本工作流的重要规则。

**开发者在 learn 中亲手完成的代码，经过 Review 后，优先考虑整合到 dev，而不是自动丢弃并采用 Codex 的参考实现。**

Codex 应比较：

1. 开发者的实现。
2. dev 中的参考实现。
3. 两者是否满足相同功能。
4. 可读性与维护性。
5. 性能与边界情况。
6. 错误处理及安全性。

如果开发者实现正确、合理且通过测试，应优先采用开发者的代码。

如果开发者实现存在问题，应先说明问题、提供修改建议，让开发者尝试修正。

只有在开发者明确同意或某实现不适合实际项目时，才使用其他实现替代。

不要求开发者的代码必须在形式上与参考代码一致。

禁止直接整体合并 learn 分支到 dev。

应该选择经过验证的文件或代码片段进行整合，避免把未完成练习带入正式代码。

## Step 8：最终测试与 Commit

完成学习和整合之后：

- [ ] 检查 dev 代码。
- [ ] 运行单元测试。
- [ ] 运行必要集成测试。
- [ ] 检查是否存在教学 TODO。
- [ ] 检查当前功能是否满足验收条件。
- [ ] 进行代码审查。
- [ ] 更新项目文档。
- [ ] 获得开发者对本次任务完成的确认。
- [ ] 在 dev 创建正式功能 Commit。

不自动 Push。

不自动合并 main。

如开发者尚未完成练习，不以开发速度为由跳过验收。

# 4. 渐进式训练难度

## L1：局部补全

适合初次接触的知识点。

Codex 完成大部分代码，留下少量 TODO。

提供：

- 输入。
- 输出。
- 主要实现步骤。
- 边界要求。
- 测试。

开发者负责补全简单代码片段。

## L2：完整函数实现

Codex 提供：

- 函数名称。
- 参数。
- 返回类型。
- 调用方。
- 测试。
- 大体实现思路。

开发者实现完整函数。

## L3：Bug 排查与局部重构

Codex 提供存在真实逻辑问题的练习代码。

开发者使用：

- 测试。
- 日志。
- 调试器。
- 源码阅读。

自主定位并修复问题。

故意错误只能存在于隔离练习环境。

不得制造可能被部署的认证或权限漏洞。

## L4：接口驱动实现

Codex 只给：

- 需求。
- 数据结构。
- 接口约定。
- 边界条件。
- 测试。

开发者自行设计主要实现逻辑。

## L5：从零开发

Codex 提供业务需求和验收目标。

开发者负责：

- 模块设计。
- 函数接口。
- 业务代码。
- 错误处理。
- 测试。
- 调试。

Codex 负责最后的 Review。

# 5. 练习代码标记规范

统一使用带等级与编号的注释。

### TODO 示例

    # TODO [L1-A] 用户名规范化
    #
    # 输入：用户提供的字符串
    # 输出：规范化后的字符串
    #
    # 实现思路：
    # 1. 去除首尾空白字符
    # 2. 返回处理结果
    #
    # 预期：
    # "  gellow  " -> "gellow"

对于尚未实现的函数，可使用：

    raise NotImplementedError("练习 A 尚未完成")

不要使用看似正常、实际返回错误数据的占位实现。

### DEBUG 示例

    # DEBUG [L3-B]
    #
    # 当前函数存在逻辑问题。
    # 请根据失败测试定位问题。
    # 不直接提供错误行号。

### REFACTOR 示例

    # REFACTOR [L3-C]
    #
    # 当前代码功能正确，但存在重复逻辑。
    # 请在保证测试通过的前提下优化实现。

每个练习必须有明确完成条件。

故意失败的练习测试应与正式项目测试区分，避免误将练习未完成当成正式构建失败。

# 6. 分级提示机制

开发者遇到困难时，Codex 应按需提供提示。

## Hint 1：方向提示

只说明应该考虑的知识点。

例如：是否可以使用字符串方法？

## Hint 2：步骤提示

把问题拆成更小的步骤，但不提供完整代码。

## Hint 3：类似示例

提供另一段相似但不同的示例代码。

## Hint 4：完整讲解

开发者明确要求，或已经多次尝试仍无法完成时，提供完整实现及解释。

开发者可以直接指定需要哪个级别的提示。

不能为了维持教学难度而拒绝明确的帮助请求。

---

# 7. 防止产生“只会填空”的问题

Codex 不应让开发者长期停留在 TODO 补全阶段。

每完成一类练习，应安排相关的迁移练习。

例如：

第一次：补全用户名校验。

第二次：独立实现邮箱字段校验。

第三次：根据需求自行定义一个数据校验函数。

逐渐减少：

- 代码骨架。
- 函数签名。
- 详细注释。
- 实现步骤。
- 测试提示。

最终要求开发者能面对一个新需求，自行决定如何组织代码。

不同领域可以采用不同难度。

例如：

- 字符串处理：L4。
- 数据库事务：L2。
- OAuth 集成：L1。
- 模块设计：L2。

不强制所有知识领域使用同一等级。

# 8. 开发者代码评价规则

每次 Code Review 使用以下评价维度：

| 维度 | 权重 |
|---|---|
| 逻辑正确性 | 35% |
| 独立完成程度 | 25% |
| 代码理解程度 | 20% |
| 边界与异常处理 | 10% |
| 可读性与维护性 | 10% |

评分只是辅助反馈，不作为机械的升级门槛。

评价时区分：

- 必须修改的问题。
- 建议优化的问题。
- 编程风格差异。

不要仅根据代码长短、是否使用高级语法评价能力。

如果开发者能用简单但正确的方式实现，不应强制换成复杂写法。

每次复盘重点应包括：

1. 开发者真正独立完成了什么。
2. 哪些地方依赖提示。
3. 哪些错误反复出现。
4. 是否具备完成类似任务的能力。
5. 是否适合提高难度。

# 10. Codex 与开发者的职责边界

## Codex 可以直接完成

- 基础项目结构。
- 前端页面。
- CSS。
- Vue 组件。
- 重复性工程配置。
- 基础测试框架。
- 不适合初学者手写的安全协议集成。
- 开发者明确授权的业务代码。

## 优先交给开发者练习

- Python 函数实现。
- 数据校验。
- 字符串和集合处理。
- CRUD。
- 简单业务逻辑。
- 错误处理。
- 权限查询。
- 模块内逻辑调整。
- 代码重构。
- Bug 定位。

复杂问题可以降低难度或让 Codex 提供完整实现，不强制开发者独立完成所有内容。

# 11. 教学工作区安全规则

- learn 不作为生产部署来源。
- 故意错误代码不得进入线上系统。
- dev 正式实现必须通过测试。
- 不在真实认证系统中故意植入安全漏洞。
- 不使用真实用户隐私数据作为训练材料。
- 不自动覆盖开发者的练习代码。
- 不将全部 learn 代码直接合并到 dev。
- 不执行未经开发者确认的破坏性 Git 操作。

如果当前任务尚未完成，可在本地保留教学进度，之后继续。

**学习任务可以慢慢做，不要求一天或一次会话完成。**

# 12. Codex 每次任务的输出格式

每次开始一个开发任务，应提供：

### 当前业务任务

说明本次要开发什么，以及在实际系统中的作用。

### 代码调用关系

说明：

- 哪个模块负责接收请求。
- 哪个函数执行核心逻辑。
- 数据从哪里来。
- 结果返回到哪里。

### 本次学习内容

说明：

- 对应知识点。
- 当前训练等级。
- 需要掌握的概念。

### 练习清单

列出：

- TODO 编号。
- 文件位置。
- 任务目标。
- 需要开发者亲手完成的部分。

### 验证方法

提供可以执行的命令和预期结果。

### 完成后的 Review

汇总：

- 测试结果。
- 代码问题。
- 学习成果。
- dev 与 learn 的实现差异。
- 最终采用的实现。
- 是否达到 Commit 条件。

对于尚未执行的测试，不得声称已经通过。

# 13. 长期训练方向

### 初期

Codex 完成大部分代码，开发者负责简单函数和局部逻辑。

### 中期

开发者逐步实现完整业务函数、数据库操作、异常处理和部分接口。

### 后期

开发者开始参与模块设计、接口划分、代码组织与测试。

### 最终

开发者能够独立完成常见 Python 后端开发任务。

Codex 主要承担：

- 架构讨论。
- 代码审查。
- 测试辅助。
- 技术资料检索。
- 复杂问题分析。
- 前端辅助开发。

不以完全不使用 AI 为目标，而以能够独立理解、判断和控制代码为目标。

# 14. Codex 首次执行要求

在正式开发前：

1. 阅读第一份项目开发规划。
2. 阅读本学习规范。
3. 检查当前 Git 分支及 Worktree 状态。
4. 检查是否存在未提交修改。
5. 规划 dev 与 learn 的建立方式。
6. 将关键规则写入或引用到 AGENTS.md。
7. 建立 LEARNING.md。
8. 保证后续正式开发不会覆盖教学代码。
9. 从项目 Phase 0 开始进行仓库审查。

首次执行不需要生成大量代码练习。

待 Phase 0 完成、Phase 1 第一个正式开发任务确定后，再启动完整双分支教学工作流。

**核心原则：Codex 可以先写出参考实现，但开发者亲手完成的正确代码，应优先成为最终项目的一部分。**

整个开发过程允许反复修改、失败、重新实现和复盘。

项目不着急上线新功能，理解代码和提升独立开发能力更重要。
